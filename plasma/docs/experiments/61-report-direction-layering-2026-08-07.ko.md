# 보고서 방향 지시의 단계별 전달

## 확인하려는 문제

이슈 #210은 보고서 요청마다 입력하는 방향 지시가 장문 보고서의 계획과 개별 섹션에만 머물지 않고, 보고서 전체에 이어져야 하는지를 다뤘다. 방향 지시는 약한 편집 축이다. 조사 내용 중 일부를 강조하거나, 특정 해석을 금지하거나, 표 같은 표현 방식을 요청할 수는 있지만, 자료에 근거한 보고를 대신하거나 미션에 필요한 범위를 줄여서는 안 된다.

## 실험 후보

후보는 사용자의 원문을 최종 기준으로 유지하면서 계획자의 가벼운 해석만 덧붙인다.

1. 장문 계획자는 계획을 확정하기 전에 사용자의 원문을 받는다.
2. 기존 보고서 구조와 `ReportWritingContract`에 그 뜻을 가볍게 반영한다. 새 저장 타입이나 프로토콜 필드는 만들지 않는다.
3. 실제 내용을 쓰는 단계에는 사용자 원문과 해석된 작성 계약을 함께 전달한다.
4. 말투 편집, 의미 검증, 근거 연결 검증, 보고서 수정, 내보내기 단계는 방향 지시 경계 밖에 둔다.

우선순위는 자료의 사실, 사용자의 명시적 원문, 계획자의 해석, 각 작성 단계의 재량 순서로 유지한다.

## 실험 방법

비교 실험은 실제 HTTP 보고서 경로와 제품 바이너리, MCP source read, 격리된 데이터베이스와 provider home, 기존 strict 장문 설정을 사용했다. 모든 비교군은 같은 source snapshot과 같은 방향 지시를 사용했다. 직렬과 `section_fanout` 전략에서 각각 기존 경로와 후보 경로를 비교했다.

방향 지시는 source 수명주기와 장기 작업의 상태 경계에 집중하고, MCP를 도메인 정책의 주인으로 해석하지 않으며, 설명을 대체하지 않는 비교표를 넣도록 요청했다.

원시 실행물은 저장소 밖의 실험 아카이브에 유지한다. 이 문서에는 공개 가능한 실험 방법, 집계 결과, 채택 판단만 남긴다.

## 첫 실행

| 비교군 | 파트 | 섹션 | 대략적인 단어 수 | 전체를 읽은 결과 |
| --- | ---: | ---: | ---: | --- |
| 기존 직렬 | 4 | 16 | 11,337 | 범위와 내용은 풍부했지만 초점이 약하고 백과사전처럼 길었다. |
| 후보 직렬 | 3 | 9 | 6,704 | 명확하고 읽기 쉬웠지만 지나치게 압축되어 필요한 범위를 잃었다. |
| 기존 병렬 | 4 | 14 | 9,838 | 첫 실행에서 가장 균형이 좋았고 요청 방향과도 자연스럽게 맞았다. |
| 후보 병렬 | 4 | 14 | 9,269 | 방향을 잘 지켰지만 구현 설명이 조금 더 빽빽했다. |

네 보고서 모두 금지한 해석과 표 요청은 지켰다. 중요한 실패는 후보 직렬 계획자가 “집중하라”는 요청을 개요를 줄여도 된다는 뜻으로 받아들인 점이었다. 이는 실제 품질 저하였으므로 첫 후보는 제품 반영 기준을 통과하지 못했다.

## 좁은 보강과 중간 확인

프롬프트 계약에 한 가지 불변 조건만 추가했다. 방향 지시는 강조점, 해석, 순서, 표현 방식을 조정할 수 있지만, 보고서 목표와 자료가 요구하는 범위와 깊이를 줄여서는 안 된다. 파트나 섹션 개수를 고정하는 규칙은 넣지 않았다.

보강 뒤에는 후보의 직렬·병렬 경로만 다시 실행했다.

| 비교군 | 파트 | 섹션 | 대략적인 단어 수 | 전체를 읽은 결과 |
| --- | ---: | ---: | ---: | --- |
| 보강 후보 직렬 | 4 | 14 | 9,331 | 요청한 중심을 유지하면서 빠졌던 범위와 깊이를 회복했다. |
| 보강 후보 병렬 | 5 | 16 | 11,092 | 요청한 중심을 유지했고 제품 경계를 폭넓게 다뤘다. |

두 보고서를 처음부터 끝까지 읽었다. Source 수명주기와 장기 상태가 글의 중심을 유지했고, 금지한 MCP 해석을 피했으며, 표와 다이어그램은 설명을 대신하지 않고 이해를 도왔다. 직렬 보고서는 첫 후보에서 빠졌던 영역을 회복했다. 병렬 보고서는 더 길고 구현 설명이 촘촘했지만, 이는 기존 장문 병렬 전략의 성향이며 방향 지시 때문에 새로 생긴 품질 저하로 보이지 않았다.

이 실행 뒤 최종 작성자와 독자 편집자에게 전체 계획 JSON을 주지 않고 `writing_contract`만 주도록 프롬프트 경계를 좁혔다. 또한 보고서 전체에 적용되는 원문을 모든 섹션이 같은 출력으로 반복하지 않도록, 구체적인 출력의 소유 섹션은 기존 요구사항 매핑이 정한다는 규칙을 분명히 했다. 이 변경은 후보의 의미를 바꾸기보다, 계획 세부사항의 과잉 전달과 출력 중복 가능성을 줄이는 마무리 보강이었다.

## 최종 후보의 제품 경로 확인

마무리 보강 뒤 최종 #210 후보 코드로 만든 같은 바이너리로 직렬·병렬 제품 경로를 다시 실행했다. Source fixture, 방향 지시, 모델, 추론 강도, strict 장문 설정은 앞선 비교와 같게 유지했다. 계획자는 파트와 섹션 개수를 고정된 목표로 받지 않았다.

| 비교군 | 파트 | 섹션 | 대략적인 단어 수 | 전체를 읽은 결과 |
| --- | ---: | ---: | ---: | --- |
| 최종 후보 직렬 | 4 | 15 | 9,976 | 소스 승인·관찰·재사용과 장기 작업 상태를 중심으로 전체 제품 경계를 유지했다. 같은 원칙을 재확인하는 문장이 병렬보다 조금 더 많았지만 흐름과 범위를 해치지는 않았다. |
| 최종 후보 병렬 | 4 | 14 | 10,800 | 제품 경계, 소스 수명주기, 장기 작업, 표시 계층으로 역할이 선명하게 나뉘었고 표와 다이어그램이 필요한 위치에만 쓰였다. |

두 최종 보고서를 처음부터 끝까지 다시 읽었다. 두 경로 모두 사용자가 금지한 “MCP가 도메인 정책의 주인”이라는 해석을 피했고, 소스 수명주기와 장기 작업 상태를 보고서의 중심축으로 유지했다. 직렬 보고서는 첫 후보처럼 범위를 축소하지 않았고, 병렬 보고서는 보고서 전체 요구사항을 모든 섹션에서 반복하지 않았다. 표는 각각 서로 다른 비교를 맡았으며 설명을 대신하는 구색 맞추기 자료로 쓰이지 않았다.

이 확인은 후보가 기존 방식보다 항상 우수하다는 통계적 결론이 아니다. 같은 실제 제품 경로와 두 실행 전략에서 최종 후보가 방향을 반영하면서도 관찰된 범위 손실이나 새로운 가독성 저하를 만들지 않았다는 제품 반영 판단이다.

실험 뒤 최신 `main`을 리베이스하면서 일반 계획형 보고서의 문체 지침과 연구 탐색에서 보고서 산출물을 숨기는 변경이 추가됐다. 두 변경은 장문 지침 선택, `source_snapshot` 읽기, 이번 방향 전달 경계를 바꾸지 않았고 리베이스 뒤 전체 테스트도 통과했다. 따라서 최종 후보를 다시 생성하지 않고 이 결과를 유지했다.

## 실행 중 확인한 별도 문제

최종 두 실행은 모두 완료됐지만, 기존 최종화 MCP 경계에서 자동 회복된 검증 오류가 관찰됐다. 대표적으로 세션 producer 불일치, UTF-8 offset 정렬, 잘못된 draft ID, 읽기 완료 전 제출이 있었고, 직렬 실행은 승인되지 않은 evidence reference를 제거한 뒤 완료됐다. 방향 지시는 말투 편집, 의미 검증, 근거 연결 검증 단계에 전달되지 않으므로, 이 문제는 이번 후보의 부작용이 아니라 기존 최종화 경로의 취약성으로 기록한다. 이슈 #210에서는 이 경계를 수정하지 않는다.

## 판단

보강한 단계별 전달 방식을 장문 보고서에 채택한다. 후보가 모든 면에서 기존 방식보다 낫다고 주장하는 것은 아니다. 최종 후보의 두 제품 경로 보고서를 직접 읽어 확인한 결론은 더 좁다. 방향 지시가 계획과 이후 작성 단계까지 이어지면서도, 첫 실행에서 나타난 범위 손실과 출력 중복은 재발하지 않았다.

이번 변경은 새 API, MCP 스키마, UI 선택지, 저장 모델, 보고서 타입을 만들지 않는다. 일반 대화, 자율 진행, 말투 편집, 의미 검증, 근거 연결 검증, 보고서 수정, 내보내기에도 방향 지시를 새로 전달하지 않는다.
